SAP Code Reviewer

User Guide & Tool Overview · Code Quality / Impact Analysis

1. What the tool does — and what it produces

SAP Code Reviewer is an automated review platform purpose-built for SAP Clean-Core development on S/4HANA Public Cloud. It accepts an uploaded project (SAPUI5 / Fiori, CAP, RAP or ABAP Cloud) and, optionally, the Functional Design document. In a single run it produces two deliverables for every project.

Primary outputs

  • A branded PDF review report — page-1 executive summary, severity break-down, Accenture Suggested Approach vs. Followed Approach, and finding-by-finding detail with code snippets.
  • A multi-sheet Excel workbook — Summary, All Findings, High / Medium / Low tabs, and one tab per detected SAP technology, with filterable columns including Source, Client Instruction and Blocks Transport.

Coverage

The findings cover security defects, Clean-Core violations, deprecated APIs and controls, performance anti-patterns, authorisation gaps, i18n hygiene, maintainability issues, test-coverage gaps, and transport blockers.

Extensibility recommendation(OPTIONAL)

When a Functional Design is uploaded, the tool additionally recommends the best-fit S/4HANA Public Cloud extensibility approach — Customisation, Key User, Developer (ABAP Cloud / RAP), Side-by-Side (BTP), or one of the two mixed approaches — and highlights any mismatch with the approach the uploaded code actually follows.

2. How it works — the big picture

The tool is a locally-hosted web application that orchestrates a Claude-powered review agent against the client project.

Step-by-step

  1. The reviewer opens the browser UI and provides a Project Name.
  2. (Optional) A Functional Design document (.doc / .docx) is uploaded in Card 1a.
  3. (Optional) Client-specific review rules are uploaded in Card 1b as .txt or .xlsx.
  4. The project source tree is uploaded in Card 2 (folder, ZIP or TAR). Non-SAP artefacts (node_modules, dist, build caches, images, test harnesses, mock data) are skipped automatically.
  5. On clicking Review, the local server launches the Claude agent, which:
  • auto-detects the SAP technology stack from file signatures;
  • applies the appropriate best-practice rule set (SAPUI5 / Fiori, CAP, RAP, ABAP Cloud);
  • honours any uploaded client rules under the "baseline AS-IS, client-priority annotation" model (baseline findings are preserved; client-sourced annotations are highlighted);
  • writes a findings JSON file to disk.
  1. In parallel, a dedicated Claude call analyses the Functional Design in full isolation from the code (so detected tech cannot bias the recommendation) and emits the extensibility verdict.
  2. The server runs the Excel and PDF exporters, which generate the client-ready reports and apply client-name masking.
  3. The UI reveals Download PDF / Download Excel buttons once both reports are on disk.

3. System requirements

  • Operating system: Windows 10 or Windows 11 (64-bit). macOS and Linux are technically supported but not QA'd for client delivery.
  • Node.js runtime: version 18 LTS or newer (version 20 or 22 recommended).
  • Claude Code CLI: installed via npm install -g @anthropic-ai/claude-code, signed in and workspace-trusted.
  • Browser: Microsoft Edge, Google Chrome or Firefox (latest two versions).
  • Network: HTTPS egress to the Claude / Anthropic inference endpoint. Corporate proxies must allow the Claude CLI's outbound call.
  • Disk space: 500 MB free for the tool, plus roughly 2× the uploaded project size for working data.
  • Memory: 8 GB RAM minimum, 16 GB recommended for large projects.

4. Prerequisites

Before first use, confirm the following are in place on the reviewer's workstation.

  • Node.js is installed and on PATH (verify with node -v).
  • The Claude Code CLI is installed globally and authenticated (verify with claude --version).
  • The workstation has one-time Claude workspace trust accepted. The server performs this step automatically on first start, but if a sandbox blocks the write to ~/.claude.json, run claude once interactively and accept the trust dialog.
  • The reviewer has read access to the client source project (typically delivered as a ZIP).
  • The Functional Design, if available, has been exported to .doc or .docx (other formats are not accepted).
  • Any client-specific review guidance has been consolidated into a .txt or .xlsx file.

5. Installation

  1. Extract the SAP Code Reviewer ZIP to a working folder, for example C:\Tools\SAP-Code-Reviewer\.
  2. Open PowerShell or Command Prompt in that folder.
  3. Run npm install. This installs the Node dependencies (exceljs, pdfkit).
  4. Verify by running node scripts/server.js. The console should print SAP Code Reviewer UI running on http://localhost:5757/. Press Ctrl+C to stop.
  5. (Optional) Create a desktop shortcut to start.cmd for one-click launch.

6. Starting the application

Typical day-to-day use follows the sequence below.

  1. Double-click start.cmd (or the desktop shortcut). A black terminal window opens and the browser launches http://localhost:5757/ automatically.
  2. Keep the terminal window visible — the review progress and any diagnostic log lines appear there.
  3. In the browser:
  • Enter a descriptive Project Name (spaces become hyphens).
  • Upload the Functional Design (optional, Card 1a).
  • Upload client-specific rules (optional, Card 1b).
  • Upload the project source tree (Card 2) — drag-and-drop a folder, a ZIP, or individual files.
  • Click Review.
  1. The progress bar runs until both reports are ready. Buttons for Download PDF and Download Excel appear automatically.
  2. To close the application, close the terminal window (or press Ctrl+C in it).

7. Output files — where everything lands

All output lives inside the reports\ sub-folder of the installation directory. Nothing is written anywhere else on the workstation.

8. Data files and refresh cadence

  • The agent rule books live in .claude\agents\*.md. They are updated whenever the Accenture SAP CoE revises its review standards; every new review automatically picks up the current rule book.
  • Review results are deterministic: the content hash of the upload tree plus the agent rule book keys the cache. Re-running an unchanged upload returns the identical PDF / Excel.
  • Clearing uploads: the UI's Clear button wipes the current project folder, the Functional Design sidecar, and the client suggestions sidecar in a single action.

10. Known limitations

  • Platform: Windows is the supported platform for client delivery. macOS and Linux work for internal use but are not QA-signed off.
  • Functional Design extraction: .docx text is extracted cleanly via inline parser; .doc (legacy binary) is best-effort text salvage and may miss embedded objects. Convert .doc to .docx where possible.
  • SAP coverage: Legacy on-prem ABAP (ECC), SAP BW/4HANA, Workflows and non-SAP microservices are out of scope.
  • Internet dependency: the Claude CLI must reach the Anthropic API. In an air-gapped environment the tool cannot run.
  • No live scanning: review is batch-oriented, not inline-in-IDE. Interactive IDE integration is on the forward roadmap.
  • Multi-project parallelism: one review runs at a time per server instance; a second request is queued or declined with a clear error message.
