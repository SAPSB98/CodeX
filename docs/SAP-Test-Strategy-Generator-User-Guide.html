SAP Test Strategy Agent — User Guide

This guide is for test managers, test leads and SAP consultants who prepare the test strategy for an SAP S/4HANA Cloud Public Edition implementation from its Statement of Work (SOW).

1. What the agent does

You provide the SOW and any later documents, such as a Fit-to-Standard output or a change request. The agent reads them and builds a reviewable test strategy, which you can edit and then generate as three deliverables:

Deliverable

What it holds

PowerPoint deck

The strategy for the client: scope, approach, cycles, entry and exit criteria, automation, governance, defects, environments, deliverables, open points

Word document

The same strategy in document form

Excel working pack

Scope, test plan, requirements traceability (RTM), automation, dependencies, RASCI, deliverables and milestones, plus SAP's S4H_438 test-plan schedule for SAP Cloud ALM

Four principles apply to everything the agent produces:

  1. The SOW is the contract. Figures and criteria are taken from the SOW and cite their source (clause, page or table). A later document can only propose changes, which you tick to apply.
  2. Tables are parsed, not guessed. Scope items, RICEFW, interfaces, waves, cycles, the RACI and the acceptance criteria are read row by row. The language model writes only the narrative that the tables do not contain.
  3. Nothing assumed is shown as agreed. Anything the SOW does not state is marked PROPOSED — requires agreement. For example, no "95% pass rate" exit criterion appears unless the SOW states one.
  4. Every gap is made visible. Sections the SOW does not cover are shown as none stated or UNREAD and are never filled in silently. Questions for the client go to the Open Points slide.

3. Step-by-step workflow

Step 1: Add the SOW

  1. Go to Setup & Inputs → Project Setup, then the Import from Documents card.
  2. Click + Add files and select the SOW, together with its annexes. Word, PDF, Excel, CSV and image files are accepted.
  3. The file list shows each file's role (SOW, annex, change request, Fit-to-Standard / Explore output, plan) and date, both taken from the document's own wording, such as its effective date. Correct either value if needed: the date determines the order in which documents are applied.
  4. Click ✨ Extract & Populate.

Step 2: Review what was read

The Review Extracted Data panel shows everything that was read before any change is made. Check three things:

  • SOW coverage. Each section is marked READ (with its count), none stated (the SOW does not cover it) or UNREAD (the agent did not recognise the layout). Treat UNREAD as a question and check the SOW yourself. An UNREAD acceptance-criteria section is shown in red, because those criteria are contractual.
  • Fidelity check. Each critical value (scope item IDs, RICEFW types, countries, waves, dates) is checked against the document's text. Any value that is not found word for word is flagged.
  • Warnings. Read every warning. Examples include:
  • Scope item names: a row whose name does not match SAP's name for its ID, or two rows that appear to be swapped.
  • The SOW states N scope items; its matrix lists M.
  • Lines of business counted as one.
  • A cycle that is not a test cycle, excluded.

Untick any section you do not want, then click ✓ Apply selected. Nothing in the project changes until you do.

  1. On Project Setup, click Clear in the file list, then add only the later document.
  2. The button becomes 🔍 Compare with the project. Click it.

The agent never treats acronyms or page numbers as scope items. In a document without a scope table, a three-character code is counted only if your SOW or SAP's index lists it, and the review names any codes that were set aside.

Step 4: Check the strategy sections

The Strategy Preview group has one page per deck section. Pay particular attention to:

  • Scope & Coverage: scope items, lines of business, RICEFW and interfaces.
  • Interfaces are counted once, from the SOW's RICEFW, using the SOW's own term for them.
  • Integration scope items stay scope items.
  • Governance & Roles: the SOW's own RACI for SIT and UAT, using the parties it names. The standard matrix appears only when the SOW does not state one.
  • Entry, Exit & Quality Gates: the SOW's acceptance criteria are quoted with their clause, and any proposed criteria appear below a "requires agreement" line.

Step 5: Run the analysis

On AI Agent Workflow, click Run Full Analysis. This populates the Analyze pages (complexity, test levels, capacity, cycles, automation, risks, decisions). These pages are internal decision support and are not included in the client deck.

Step 6: Set the test plan

On Analyze → Capacity Planning, the Tentative Test Plan card calculates the test cases and weeks per cycle (see section 5).

  • Set the assumptions to match your team: testers, days per week, productive hours, hours per manual and automated case, and the factors.
  • Enter the end-to-end scenarios from Fit-to-Standard, one per line, in the format "Name: scope item IDs". Until you do, UAT is sized on a PROPOSED estimate.
  • Optionally, set a test start date to place the plan on a calendar.

Step 7: Edit, then generate

  1. Open Generate → Edit Strategy. You can change any slide text or figure here, and each edit is tracked:
  • Each field shows its basis (SOW, SAP, PLAN, PROPOSED). Changing a field marks it as EDITED.
  • Marking a proposal as AGREED requires the name of the person who agreed it and the date.
  • You can switch individual slides off, and Preview deck shows the result.
  1. Open Generate → Generate Strategy and click Generate PowerPoint, Generate Word document and Generate Excel working pack.
  2. The Test Schedule (S4H_438) sheet in the Excel pack is SAP's test-plan schedule, ready to import into SAP Cloud ALM. Once cycles are under way, fill in its statuses (or export them from Cloud ALM). Then import the file on Analyze → Cycles & Gates using ⬆ Import S4H_438 schedule or Cloud ALM export to evaluate the quality gates.

Step 8: Save and share

  • Work is autosaved in the browser and, on your machine, on disk. The header shows the time of the last save.
  • ⬇ Export file saves the whole project as a single JSON file, and ⬆ Import file loads it back. Use these to back up your work or hand it over to a colleague.
  • In Claude, the Saved Projects card keeps named versions in claude.ai storage.
  • Saved data is never carried over from one engagement to another.

The Open Points slide groups everything that needs attention by type:

  • Recommendation: an action the project team advises.
  • Gap to discuss: something is incomplete or inconsistent.
  • Input needed: a client decision or fact is required.
  • Assumption: a default the strategy proceeds on, to be validated.

Each point has an owner and a priority. Work through them during the review, close those that are settled, and carry the rest into the project log.

5. How the figures are calculated

Scope items. The rows of the SOW's scope matrix. Items added by a later document, once ticked, are counted separately: "N from the SOW's scope matrix + M added from …".

Lines of business. The SOW's process areas, counted once per stated area. Spellings that the client has confirmed refer to the same line of business (for example, "Service" and "Services") are merged, and the slide says so.

Interfaces / integrations. A single figure, using the SOW's own term, taken from its RICEFW. The interface table only names the connected systems, unless the RICEFW lists no interfaces, in which case the table provides the figure. The connected systems are a breakdown, never a second count.

Test cases (driver model):

  1. One full SIT pass = business processes (one positive path per scope item) + negative paths (one per positive path; PROPOSED unless the SOW requires negative testing) + interfaces (one case each) + custom objects (each non-interface RICEFW object, with Complex objects counted twice). Complexity is taken from the object itself or, where the RICEFW register states none, from the Complex count in the SOW's RICEFW summary for that type.
  2. SIT 1 runs the full pass. Later SIT cycles run a share of it as regression, set by the later-cycle factor (0.6 by default).
  3. Each UAT cycle = the end-to-end scenarios + the user-facing RICEFW objects (reports, forms, enhancements, workflows).
  4. Cycles are those the SOW states: its billing rows, or SIT 1 / SIT 2 / UAT as named in its milestones or test timeline. The language model is consulted only when the SOW names none.
  5. Waves after the first run a share of the work (the later-wave share). The number of weeks follows from the cases, the hours per case and the number of testers.

Example:

  • A SOW with 40 scope items, 6 interfaces and 20 other RICEFW objects (3 Complex) has one SIT pass of 40 + 40 + 6 + 23 = 109 cases.
  • SIT 2 is 0.6 × 109 ≈ 65.
  • UAT is the scenarios + the user-facing objects.

Automation verdicts (Automation Assessment) indicate when to automate: Automate now, Automate later (from SIT 2), Keep manual, or Do not automate. They are based on four scores: frequency, stability, regression value and maintenance effort.

Automation routes indicate how to automate:

  • An SAP-delivered automate (automated test script) in SAP TAT, where SAP's S4H_640 lists one.
  • Otherwise, manual. A custom automate would have to be built and maintained by the project, which the SOW does not assume.
  • Connected systems are routed according to how they integrate.

6. The checks that protect accuracy

Check

What it catches

Coverage

A section the agent could not read (UNREAD), kept distinct from one the SOW does not state

Fidelity

A value not found word for word in the document

Name check

A scope row whose name is SAP's name for a different ID, or two rows that appear to be swapped (requires SAP's index)

Stated totals

The SOW's stated count compared with its matrix, and a later document's count compared with the SOW's, by line of business

Interface conflict

A mismatch between the interface table's count and the RICEFW count, raised as an open point

Later documents

Changes are listed for you to tick; codes found outside a scope table are set aside; values a document omits are never treated as changes

7. If something looks wrong

Symptom

What to do

A section is UNREAD

Locate the section in the SOW. If it is there, its layout is not yet recognised: note the page number and raise it. The slide shows what is missing rather than a default

A count does not match what you expect

Read the slide's How calculated line and the review warnings. A later document may state a different figure; see Changes since the SOW

A scope item's name is flagged

Confirm with the client which scope item the contract refers to. The agent tests the IDs as stated

Extraction is slow

On a laptop the first run takes minutes. Keep the tool's window open; a re-run of the same document is answered from the cache

A PDF yields little text

It may be scanned. On your machine the images are read by OCR; check the review's page count

Changes from an earlier document cannot be applied

They are marked "Before the SOW — tick to adopt". Tick the ones you agree with
